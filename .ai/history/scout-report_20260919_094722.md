## Relevant Files, Symbols, and Execution Paths

- **`src/main.js`**: Core application bootstrap. Manages the synchronized Three.js/CesiumJS render loop (`animate()`), bootstraps aircraft models (`buildAircraft`, `buildSR71`), registers input callbacks via `createControls`, updates flight physics (`updateFlightModel`), and triggers visual effects (`updateWarpEffect`). Any projectile or fireball system must hook into this main loop for spawning, updating, and rendering.
- **`src/effects.js`**: Currently houses `buildWarpEffect` and `updateWarpEffect`, which manage the 10× boost streak lines using `THREE.LineSegments` and procedural geometry updates. The fireball particle system would logically attach here or be split into a new dedicated module.
- **`src/controls.js`**: Handles keyboard event listeners and maps keys to boolean inputs (`KEY_MAP`, `keydown`, `keyup`). Maps `KeyB`/`Space` to boost, but contains no mappings for weapon firing. A new key (e.g., `KeyX`) and callback would be required.
- **`src/cesiumWorld.js`**: Provides `getGroundHeight(x, z)` and `sampleGroundAt(lat, lon)`, which sample Cesium's terrain height asynchronously. Accurate ground-collision checks for missile impacts must route through this function to avoid clipping on procedurally loaded tiles.
- **`src/flightModel.js`**: Maintains `FlightLimits` and `createFlightState`. While not directly involved in weapons, weapon state (ammo, cooldown, availability per aircraft mode) could be attached to the flight state object.
- **`public/data/landmarks.json`**: Defines mission objectives. No weapon-related data exists.

**Execution Path for Missiles/Fireball (Target Implementation):**
`key down` → `controls.js` fires `onFire` callback → `main.js` passes input to new missile module → spawns projectile entity synced to aircraft pose → each frame runs trajectory integration → performs ground-height query via `cesiumWorld.sampleGroundAt` → upon intersection, destroys projectile, spawns `THREE.Points`/`Sprite` fireball at impact coordinates → fireball expands over N frames → removal.

## Observed Behavior vs. Hypotheses

**Observed Behavior:**
- The codebase is a fully functional arcade flight simulator with CesiumJS terrain streaming, Three.js aircraft compositing, HUD overlay, and a 10× rocket boost system (`src/effects.js`, `src/flightModel.js`).
- There is absolutely no code handling projectile physics, weapon state, bullet/cannon logic, or particle explosions/fireballs. Searching all provided `.js` and `.json` files yields zero matches for keywords like `missile`, `shoot`, `fireball`, `explosion`, `particle`, `spawn`, `ammo`, `weapon`, or `raycaster`.
- Input mapping (`src/controls.js`) explicitly binds `B`/`Space` to boost, `F` to camera, `G` to aircraft toggle, and standard WASD/arrows to flight controls.

**Hypotheses:**
- The requested "5x larger fireball" implies a previously scoped feature that was either deferred, never coded, or removed before this snapshot was taken.
- Implementing this requirement effectively constitutes building the entire missile-and-explosion subsystem from scratch, rather than incrementally scaling an existing component.
- Baseline assumptions about fireball size, duration, color palette, and sound (if audio were planned) are unavailable, meaning visual design parameters must be defined.

## Risks, Unknowns, and Specific Open Questions

- **Rendering Performance**: Dynamically spawning expanding particle meshes each frame adds draw calls. Without pooling and batched geometry, FPS may drop significantly over large untracked ground areas.
- **Terrain Collision Sync**: Cesium terrain tiles load asynchronously. Projectiles raycasting against a static flat plane will pass through the viewport. Collisions must query `cesiumWorld.sampleGroundAt` or Cesium's native scene picking, introducing latency if not cached.
- **Scope Creep**: Weaponization introduces game-mechanic concerns (ammo limits, cooldowns, hit registration, visual feedback/flashbacks) that sit outside the current free-flight scope.
- **Dependency Footprint**: Relying purely on primitive Three.js geometries keeps the project dependency-free, but achieving "very easy to see" visuals may require custom shaders (fresnel/glow/bloom) or post-processing chains not currently initialized.
